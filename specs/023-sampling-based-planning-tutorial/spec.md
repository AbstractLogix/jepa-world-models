# Feature Specification: Sampling-Based Planning Tutorial

**Feature Branch**: `023-sampling-based-planning-tutorial`
**Created**: 2026-10-15
**Status**: Draft
**Input**: Project goal to deliver roadmap lessons with reproducible local evidence; recent paper on tree search with world models.

## User Scenarios & Testing

### User Story 1 - Compare tree search with trajectory optimization (Priority: P1)

As a learner, I want to compare tree-based search with a shooting optimizer on a task that requires a detour, so I can see how each planner explores possible futures.

**Why this priority**: A recent paper applies RRT and KPIECE search to world-model states and reports that tree search can handle detours with fewer model evaluations than CEM or MPPI. The paper's official lab listing links a PDF and video but no code. A small local analogy can teach the search methods while keeping the paper evaluation separate.

**Independent Test**: Run every notebook code cell in a fresh CPU kernel. Confirm that RRT, KPIECE, and CEM use the same toy transition model, the same paired task starts, and equal maximum transition-evaluation budgets. Confirm that the report labels all local results as an illustrative state-space analogy.

**Acceptance Scenarios**:

1. **Given** a point-mass task with momentum and an obstacle between the start and goal, **when** the learner runs RRT and KPIECE, **then** each planner stores reachable intermediate states, avoids invalid transitions, and can return a path that goes around the obstacle.
2. **Given** the same task, toy model, starts, and per-decision evaluation budget, **when** the learner compares RRT, KPIECE, and CEM, **then** the notebook reports paired closed-loop outcomes, steps, transition calls, and runtime for each method.
3. **Given** the paper's reported results, **when** the notebook discusses them, **then** paper values remain separate from local measurements and the notebook states that it does not use DINO-WM, learned latents, paper checkpoints, or robot tasks.
4. **Given** a clean project environment, **when** the notebook runs, **then** it needs no downloaded data, model weights, robot hardware, or added dependency.

## Requirements

### Functional Requirements

- **FR-001**: Explain the paper's receding-horizon search method and distinguish its nearest-neighbor-guided RRT, projection-guided KPIECE, and optional CEM trajectory polishing.
- **FR-002**: Use one explicit toy task with momentum, obstacles, a start region, a goal region, and one ground-truth transition rule.
- **FR-003**: Compare RRT, KPIECE, and CEM using the same task definition, transition model, paired starts, and maximum transition-evaluation budget per planning decision.
- **FR-004**: Report the task, planner settings, evaluation seeds, episode limit, success definition, closed-loop success, steps, model-transition calls, runtime, and variation across evaluation-seed groups.
- **FR-005**: Preserve failed or missing episodes in the planned denominator and report the count of missing or errored runs.
- **FR-006**: Label the lesson as an illustrative state-space analogy. Do not call it a learned world model, JEPA implementation, paper reproduction, or physical-robot validation.
- **FR-007**: Align the README, curriculum, evaluation protocol and audit, roadmap, reproduction matrix, project research, project task ledger, alignment record, and remaining-work record with the lesson and the separate paper-reproduction gate.

### Out of Scope

- Reimplementing DINO-WM or training any visual world model.
- Reproducing the paper's four simulated domains, DINO-WM task sets, rope data, or YAM robot experiment.
- Claiming that local planner results validate the paper's success or runtime claims.
- Downloading paper data, checkpoints, or third-party code.
- Adding a planner library, general-purpose benchmark framework, or dependency.

## Key Entities

- **Toy task**: A fixed point-mass system, obstacle map, start distribution, goal region, and episode limit.
- **Planner**: RRT, KPIECE, or CEM with a declared per-decision transition-evaluation budget.
- **Episode**: One planner's run from a shared start under one fixed evaluation seed.
- **Evaluation group**: A declared seed grouping used to report episode variation; it is not a training run.
- **Paper claim**: A value reported by the paper on its own learned model, task set, compute, and evaluation protocol.
- **Local measurement**: A result regenerated by this repository for the hand-authored toy task.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Every code cell completes in a fresh CPU kernel without downloading external data or model assets.
- **SC-002**: The notebook evaluates at least 20 common starts in each of five declared evaluation-seed groups and reports paired results for every planner.
- **SC-003**: RRT, KPIECE, and CEM share the same task, toy transition rule, and maximum transition-evaluation budget per planning decision; actual transition calls are reported.
- **SC-004**: The local report includes success, steps, model-transition calls, runtime, per-group variation, and missing/error counts.
- **SC-005**: The notebook and report state at least three limits of the analogy and do not present local measurements as paper results.
- **SC-006**: Every project index that lists current lesson coverage identifies Notebook 21 as illustrative and keeps the official paper evaluation separate.

## Assumptions

- The primary source is the v1 paper [Sampling-based Kinodynamic Planning with World Models](https://arxiv.org/abs/2610.12910), submitted on 2026-10-09 and listed as under review.
- The CoMMA Lab publication entry is authoritative for current author-linked artifacts. It lists a PDF and video for this paper but no code link; the separate PAKR code link belongs to a different paper.
- A state-space point-mass example can teach the search structure without implying that it tests learned latent representations or the paper's findings.
- The paper-scale evaluation remains a candidate until its exact planner code, model artifacts, task files, and evaluation protocol are available and the required runtime is qualified.
